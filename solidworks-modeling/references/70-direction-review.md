## 0. 一句话结论

**没走偏，但走窄了。**

方向（声明式计划 + 真机双证）是对的，而且第一层的**横向覆盖已经够用**；
问题在于过去两个里程碑的验收判据只覆盖了「**能不能建出形状**」，
没有覆盖「**建出来的东西能不能改、能不能复用**」。

后果是一类**结构性的假通过**：形状对、错误码 0、图上看着对，
但改一个尺寸就变形（草图零约束）、或者名字按界面语言漂移（中英混名）。
**这类问题探针抓不到** —— 探针只会说"这步没抛异常"。

## 2. 第一层（基础能力）判断

### 进展
横向覆盖够用（见 1.2）；"不猜参数"这条硬规则已经靠 `--tlb` 落地，并因此抓出过 8 个错的 API 名。
**这一层不是不够宽，是不够硬。**

### 差距（4 个，按严重度排）

**① 草图零约束 ← 最严重。**
`sketch_begin` 为了速度开了 `AddToDB=True`（跳过推断/自动约束）。
实测：一个矩形草图 `GetConstrainedStatus()` = **2（UnderConstrained）**。
**这意味着"参数化"这个卖点目前是不成立的** —— 改一条边，其他三条不跟着动。

**② 命名按界面语言漂移。**
中文模板下实测：基准面 `前视基准面/上视基准面/右视基准面`；轴叫 `基准轴1`；配置叫 `默认`；草图叫 `草图1`。
代码里是**打地鼠式**的 `try 中文 / 再试英文`（散落在 `select_plane` / `axis_from_planes` / `_active_config_name` / `circular_pattern` 里），不是机制。

**③ 没有 GB 标准值表。**
`gb_standard.json` 在 M1 计划里，至今未建。而且参照件实测已经和国标常规值**对不上**：
平垫圈 10 实测 Ø22 × 1.5、螺钉 M3 头部 Ø6.0。**"跟图纸"还是"跟国标"这个口径不定，标准件准返工。**

**④ Agent 可调用性差一层。**
59 个 op 的目录只能人读（`--cat`）或出 Markdown（`--write-md`），**没有机读 schema 导出**；
`verified` 只是布尔，**没有"已知边界"字段**（比如 `hole_wizard` 建不出盲孔/螺纹孔这件事，只写在文档正文里）。

### 方向偏差：有，且很具体
> **验收判据缺了一条维度。**

现在的三级验收是：① 特征树新增 ② `GetErrorCode == 0` ③ 几何量对得上。
这三条能抓住"没建出来"和"建错了"，但**抓不住"建出来了、但是不可改"**。

`chamfer` 上一轮那次假通过（特征在、错误码 0、一料不去）是同一个病根的另一张脸：
**判据只覆盖"存在性"，不覆盖"有效性"**。草图欠约束属于同一族 —— 形状存在、几何正确，但**参数化失效**。

### 优先补齐 / 验证

**① ⭐ 草图约束层 —— 已真机验通，可以直接落地**

本轮实测（`D:/out/m3_probe.json`）：

| 验证项 | 结果 |
|---|---|
| `ISketch.GetConstrainedStatus()` | **可用** → AddToDB 矩形 = `2 UnderConstrained` |
| `ISketchManager.FullyDefineSketch(True,True,1023,True,1,None,1,None,1,1)` | **状态码 0 = Success** |
| 调用后草图状态 | `2 UnderConstrained` → **`3 FullyConstrained`** |

`swSketchFullyDefineRelationType_e` 正好是你要的"标准约束"十种：
`Horizontal(2) / Vertical(4) / Coincident(512) / Parallel(128) / Perpendicular(16) / Tangent(8) / Equal(1) / Concentric(64) / Colinear(32) / Midpoint(256)`。

落地三件套：
- `sketch_fully_define`（op，包 `FullyDefineSketch`，`relations` 位掩码可配）
- `sketch_relation`（op，包 `IModelDoc2.AddRelation(RelStr)` —— **真签名是 1 个字符串参数**）
- `check_sketch_constrained`（**验收判据**，读 `GetConstrainedStatus`，非 3 就报错）
- 并且把 `AddToDB` 策略改成「**默认 False，明确要提速才开**」—— 现在是反的。

**② ⭐ 命名规范层 —— 也已真机验通**

| 验证项 | 结果 |
|---|---|
| `ISldWorks.GetCurrentLanguage()` | 返回**字符串** `"chinese-simplified"`（**不是** `swUserPreferencesLanguages_e` 的整数 —— 照文档猜会踩坑） |
| `IFeature.Name` 可写？ | **可写**。把"草图1"改成 `Sketch1_EN`，读回一致 |

方案：一张 `assets/naming.json` 存 `{canonical_en, aliases:{cn, tw}, kind}`；
op 层统一走 `resolve_name()`；建完统一走 `normalize_names()`（把特征名刷成英文主名）。
**英文为规范主名、中文做别名** —— 英文名稳定、能进文件、不随语言变。

**③ GB 标准值表**（最小集，每个值必须标出处 = GB 号 + 表号）
螺钉 GB/T818 · 螺栓 GB/T5782 · 螺母 GB/T6170 · 平垫 GB/T97.1 · 弹垫 GB/T93 · 键 GB/T1096 · 销 GB/T117 · 轴承 GB/T276。
**先定口径再录数**。

**④ `sw_ops.py --schema`** 导出机读 JSON：op 名 / 参数 / 类型 / 单位 / 前置状态 / `verified` / **已知边界**。

## 4. 第三层（远期：自然语言 / 图纸 → 设计+建模+装配）判断

### 进展：两条"半条路"，都断着
- **自然语言 → 计划**：靠 Agent 读文档手写 JSON。**没有**"需求 → 设计方案"这一层。
- **图纸 → 参数**：`sw_macro_to_plan.py`（宏翻译）有了；**图纸识别也有，但长在另一个项目里**
  （YoYo 的 `yoyo/ocr.py` + `yoyo/dimension.py` 截图识别尺寸）。**两边没接。**

### 差距：最大的是**"设计"整层不存在**
现在能做「给定参数 → 建模」，不能做「给定工况 → 选型」。而比赛图纸其实**已经给了设计结果**
（m=2 / z₁=15 / z₂=55 / a=70 / h=80），所以第二层**不需要**设计层；
但第三层的"自然语言即可独立完成设计"**必须有**选型校核层：
传动比与分配、模数与齿数、中心距、轴径估算、轴承寿命、齿根弯曲/齿面接触强度、键的挤压强度。

### 方向偏差：⚠️ 风险不在"走偏"，在"顺序"
第三层依赖第一层的约束体系和第二层的参数表。
**现在若先去接 OCR 图纸识别，等于把已经被点名的最大风险"尺寸抄错"放大** ——
OCR 错一个数字，整套零件全废，而且极难回溯（错在源头，下游看起来全部"通过"）。

### 正确的接入点（想清楚了再动手）
```
图纸/截图 → OCR → 候选值 + 置信度 → 【人确认闸门】 → reducer.params.json → 计划 → 建模
```
闸门直接复用 YoYo 已有的**待确认机制**（OCR 尺寸入库默认 `is_confirmed=0`），
以及"Ø 认成字母/前导 0 要降权"那一套抢救规则。**参数表是唯一的数据源，人工只审这一处。**
